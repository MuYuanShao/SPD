### 列宽排名与权重（按实测内容自然宽度）

列宽不是拍脑袋定的。先用 canvas 按**真实字体**量出每列每一行内容的自然宽度，
再据此排出名次、换算成权重，最后**按权重比例铺满内容区**。

| 排名 | 列 | 内容 P90 | 权重 | 保底 | 上限 |
| --- | --- | --- | --- | --- | --- |
| 1 | 商品名称 | 789 | **9** | 104 | 560 |
| 2 | 生产厂家 | 464 | **7** | 104 | 420 |
| 3 | 规格型号 | 188 | **5** | 104 | 280 |
| 4 | 科室 / 库房 | 156 | **3** | 119 | 175 |
| 5 | 更新时间 | 148 | **3** | 104 | 175 |
| 6 | 商品编码 | 132 | **2** | 104 | 150 |
| 7 | 维护来源 | 56 | **2** | 56 | 105 |
| 8 | 状态 | 28 | **2** | 56 | 92 |
| — | **操作**（固定列） | 3 个按钮 ≈ 150 | **3** | 150 | 210 |

分配机制（`useListColumns.ts` → `effectiveWidths`）：

1. **基准 = 用户设定值** —— 拖拽结果最高优先级，不会被按比例分配覆盖。
2. **富余按权重比例分配** —— 受各列 `maxWidth` 上限约束；
   某列到顶后超出部分回收，重新分给还有空间的列。
3. **不足按权重比例压缩** —— 受各列 `minWidth` 保底约束。
4. **hybrid 额外调剂** —— 为未达「理想宽度」的长文本列（如规格型号）
   从有余量的列按比例借调，**借多少还多少，总量始终守恒**。

#### 关键修复：超宽屏（≥2560px）右侧留白

**问题现象**：在 2560px 及以上的宽屏上，表格右侧出现大片留白，没有铺满内容区。

**根因**：每列都有 `maxWidth` 上限（商品名称 560 / 生产厂家 420 / 规格型号 280 …）。
当视口宽到一定程度，**所有列同时触顶**，富余分配循环找不到任何还有空间的列，
剩余宽度就无处可去，直接变成右侧空白：

| 视口 | 内容区宽 | 修复前列合计 | 修复前留白 |
| --- | --- | --- | --- |
| 1920px | 1884 | 1882 | 2px |
| 2560px | 2524 | 2215 | **309px** |
| 3440px | 3404 | 2215 | **1189px** |

**修复**：富余分配循环结束后，若仍有剩余（说明全部列都已触顶），
**解除 `maxWidth` 上限约束再按权重比例分配一次**，
保证 100% 铺满内容区，且不产生横向滚动。

```ts
// —— 兜底：所有列都触到 maxWidth 上限后，剩余宽度必须**无上限地**
//    按权重比例分给各列，否则超宽屏（≥2560px）会出现右侧留白。
if (pending > 0.5) {
  const wSum = /* 各列权重之和 */
  for (const column of cols) widths[column.key] += (pending * weightOf(column)) / wSum
  for (const column of fixedCols) widths[column.key] += (pending * fixedWeight(column)) / wSum
  pending = 0
}
```

**修复后实测**（表头列合计 vs 内容区宽）：

| 视口 | 内容区 | 表头合计 | 差值 | 横向滚动 |
| --- | --- | --- | --- | --- |
| 1280px | 1244 | 1241 | 3px | 无 |
| 1920px | 1884 | 1882 | 2px | 无 |
| 2560px | 2524 | 2520 | 4px | 无 |
| 3440px | 3404 | 3403 | 1px | 无 |

差值 1–4px 来自 Element Plus 的滚动条与边框舍入，视觉上无空白。

#### 「操作」列也参与比例分配

早期版本把「操作」列写死 `width="200"`，并从可用宽度里硬扣掉（`reservedWidth: 248`）。
这会导致：

- 操作列不随视口变化，宽屏下凭空占掉 200px；
- 更关键的是，**被硬扣掉的部分没有进入比例分配池**，
  「商品名称」这类字最多的列拿到的比例被无谓压低。

改法（`useListColumns` 新增 `fixedColumns` 选项）：

```ts
fixedColumns: [
  { key: 'actions', label: '操作', width: 170, weight: 3, minWidth: 150, maxWidth: 210 }
]
```

- 操作列与数据列进入**同一个权重池**竞争剩余宽度；
- `reservedWidth` 只保留选择列的 48px；
- 固定列不进入「列设置」面板（不提供显隐开关），但会参与比例分配；
- 操作列权重取 3 —— 只有 3 个按钮（编辑 / 启用 / 删除），实际约需 150px，
  权重应低于「商品名称 / 生产厂家」，避免抢走字多列的空间。

效果：1920px 下操作列 210px（达上限），1280px 下 172px，
表格在任何视口都**恰好铺满内容区**，剩余宽度按权重比例分给所有列。

| 生产厂家 | 464 | 156 | **7** | 104 | 420 |
| 维护来源 | 56 | 71 | 2 | 56 | 105 |
| 状态 | 28 | 71 | 2 | 56 | 92 |
| 更新时间 | 148 | 126 | 3 | 104 | 175 |

基准宽度合计 **996**（+ 选择列 48 + 操作列 200 = **1244**），
恰好等于 1280px 内容区宽度，因此最窄屏也刚好铺满。

- **字多的列给足空间** —— 权重 9 / 7 / 5，1920px 下拿到 372 / 313 / 253px。
- **字少的列保持紧凑** —— 状态 92px、维护来源 105px（内容仅需 28 / 56px），
  任何视口下都不会出现大片空白。
- **用户拖拽最高优先级** —— 拖拽后的宽度被持久化，
  按比例分配只在其基础上增减，不会覆盖用户意图（实测：状态列 81 → 143px，刷新后保持）。

## 七之二、表头分隔线可见性（重要修复）

**问题根因**：表头单元格的 `background` 与 `border-color` 原本都是 `--ulc-primary`
（同一个深色主色），导致列分隔线与背景**完全同色、彻底隐形**，
用户看不出哪里能拖拽调整列宽。

**修复方案**（`frontend/src/styles/list/unified-list.css`）：

```css
/* 表头分隔线：主色 + 32% 白，比底色明显提亮 */
.spd-unified-list .ulc-table .el-table__header th.el-table__cell {
  background: var(--ulc-primary) !important;
  border-color: color-mix(in srgb, #ffffff 32%, var(--ulc-primary)) !important;
}

/* 悬停时进一步提亮，明确提示「此处可拖拽」 */
.spd-unified-list .ulc-table .el-table__header th.el-table__cell:hover {
  border-right-color: color-mix(in srgb, #ffffff 65%, var(--ulc-primary)) !important;
}

/* 拖拽中的代理线改为纯白 2px，落点始终清晰 */
.spd-unified-list .ulc-table .el-table__column-resize-proxy {
  border-left: 2px solid #ffffff !important;
}
```

实测（浏览器 computed style）：

```
表头底色   = rgb(31, 111, 109)
表头分隔线 = color(srgb 0.403 0.616 0.611)   ← 明显亮于底色
数据行分隔线 = rgb(213, 224, 229)
```

**拖拽可用性实测**（Playwright 真实鼠标拖拽）：

```
right-1px → cursor="col-resize"   ← 悬停即有拖拽光标
right-2px → cursor="col-resize"
...
拖拽中代理线 = { display: "block", border: "2px rgb(255,255,255)" }
拖拽后商品名称 = 300 → 342（宽度生效）
localStorage 已持久化
```

放大截图见 `output/header-zoom.png`（表头分隔线与数据行分隔线在同一竖线上）。

## 十、推荐方案

### 推荐：**方案 C（混合列宽 + 典雅松竹绿）**

**理由：**

1. **默认恰好铺满内容区** —— 表格宽度始终等于内容区宽度，
   右侧不留空白、不出横向滚动（1920 → 1884px，1280 → 1244px）。
2. **字多的列给足空间** —— 权重 9 / 7 / 5，1920px 下
   「商品名称」372px、「生产厂家」313px、「规格型号」253px，
   65 字符极限数据几乎不折行，信息完整不截断。
3. **字少的列保持紧凑** —— 1920px 下「状态」92px、「维护来源」105px，
   与实测内容宽度（28px / 56px）仅留必要余量，**没有大片空白浪费**。
4. **用户意图优先** —— 拖拽后的宽度即基准，不会被按比例分配覆盖，
   刷新后保持（实测：状态列 81 → 143px）。
5. **配色最耐看** —— 松竹绿 `#245b45` 明度低于青玉，浅底深字对比柔和，
   长时间连续值班的疲劳感最低。

### 若更看重「列宽完全可控」，选方案 A

用户拖拽后列宽**绝对锁定**，不会因视口变化而重排（1920px 与 1280px 列宽完全一致）。
代价是窄屏下右侧会留空白（表格恒为 1244px），
且长文本列恒定在 171 / 156px，65 字符商品名需换行多行。

### 方案 B 作为最终态的取舍

方案 B 与方案 C 在 1920px 下表现完全一致（都是按权重铺满）。
差异只在窄屏：

- **无调剂机制** —— B 不为「规格型号」做理想宽度调剂，
  1366px 下规格型号只有 154px（换行显示），C 为 175px（更接近单行放下）。
- **短列略松** —— 代价是 C 在窄屏下短列收得更紧
  （1366px：科室 119 vs B 的 148，维护来源 56 vs 76）。

若确定只在 1366px 以上使用，两者差异很小；若需兼顾 1280px 窄屏笔记本，C 更稳。

### 落地方式

当前三个方案分支并列存在，选择后把对应分支的
`frontend/src/styles/tokens/palette-X.css` 与 `frontend/src/styles/layout/column-strategy-X.css`
合并进 `feature/ui-readability-base` 即可，无需重写业务代码。

> 注：三个分支的列宽分配算法（`useListColumns.ts`）、列权重配置
> （`CATALOG_COL_DEFAULTS`）与表头分隔线样式（`unified-list.css`）已保持完全一致，
> 差异只在 `fitMode` 取值（fixed / fit / hybrid），
> 因此对比结果反映的是策略本身的差异，而非实现差异。

## 十二、方案 D：暗夜黑（Night Black）—— 独立页面分支

> 分支：`feature/ui-dark-night`
> 页面：`/features/department-warehouse-catalog-night`
> 浅色原版 `/features/department-warehouse-catalog` **完全不受影响**，两条路由可随时对照切换。

### 12.1 设计定位

前三套方案（A 青玉 / B 蓝灰 / C 松竹绿）都是**浅底深字**，
适合白天明亮环境下的长时间值守。方案 D 面向**夜间值班、值班室灯光偏暗、
或大屏巡检**场景，提供一套**暗底浅字**的独立配色。

它不是「把浅色模式反色」，而是重新设计的一套配色：

| 维度 | 浅色三方案（A/B/C） | 方案 D 暗夜黑 |
| --- | --- | --- |
| 底色 | 近白 / 浅灰渐变 | `#0b0f14` 近黑冷灰蓝 |
| 文字 | 深色 `#1f2933` / `#101820` | 浅灰白 `#e8edf3` / `#f2f6fa` |
| 主色 | 青玉 / 蓝灰 / 松竹绿 | 琥珀金 `#d8a24a` |
| 色温倾向 | 冷（医疗洁净感） | 冷底 + 暖金强调，暖冷对冲 |

**为什么用琥珀金而不是直接反色青玉**：暗底上若沿用青玉，
主色与背景明度差不足、按钮会「陷进」背景里；
琥珀金在 `#0b0f14` 上对比强但不刺眼，且与冷色底形成唯一的暖点，
让「可操作」元素在暗屏上一眼可辨。

### 12.5 主题隔离机制

暗夜黑通过**独立属性** `data-spd-theme="night-black"` 挂在 `<html>` 上，

- 顶栏切换用户主色**不会**覆盖暗夜黑方案；

- 同一套三档字号系统（标准 / 大 / 特大）。

方案页与浅色原版通过不同路由访问，评审时可在两个地址之间切换同屏对照。

## 十三、方案 E：静墨宣纸（Calm Ink Paper）—— 第三套设计方案

> 分支：`feature/ui-calm-paper`
> 页面：`/features/department-warehouse-catalog-calm`
> 浅色原版 `/features/department-warehouse-catalog` **完全不受影响**。

### 13.1 设计出发点

前三套方案（A 沉静青玉 / B 静谧蓝灰 / C 典雅松竹绿）以及方案 D 暗夜黑，
本质是**同一套页面骨架换不同色相**。逐套对比下来会发现一个共同问题：

> 页面的「视觉墨量」始终没有变过 —— 满表格竖网格线 + 重色表头实底 + 斑马纹
> + 0.4 透明度的大面积状态块。这四样东西才是长时间看累的真正来源，
> 单纯降低主色饱和度解决不了。

方案 E 因此**不再只改颜色，而是同时降低信息密度**，
把「表格像一张 Excel 打印稿」改成「表格像一份可读的报告」。

### 13.2 六项降噪改动

| # | 改动 | 前三方案 / D | 方案 E | 减负原理 |
| --- | --- | --- | --- | --- |
| 1 | **表格竖网格线** | 全列竖线 | **全部取消**，只留横线 | 竖线是眼动最大负担，等于把每行都切成格子 |
| 2 | **斑马纹** | 有（`--ulc-row-stripe`） | **取消**，改用极淡横线分隔 | 双色交替会在余光里形成明暗抖动 |
| 3 | **表头** | 主色实底 + 白字（大色块） | **浅墨底 + 墨色字** + 底部加重横线 | 表头不再是最重的视觉块，视线从表头移到数据 |
| 4 | **状态条底色** | 语义色 0.4 透明度 | **语义色 0.14 透明度** | 颜色仍可辨，但不再在屏幕上形成色面 |
| 5 | **底色色温** | 冷白（青玉/蓝灰系） | **宣纸暖白**（去冷蓝倾向） | 冷蓝底长时间注视更易疲劳 |
| 6 | **阴影** | 有卡片投影 | **几乎不用阴影**，层次靠 1px 描边 | 投影在大面积表格上会形成脏边 |

### 13.3 配色（全局仅 5 个色相）

| 角色 | 色值 | 说明 |
| --- | --- | --- |
| 宣纸底（页面） | `#f6f3ec` | 暖白，无冷蓝倾向 |
| 宣纸底（卡片） | `#fdfbf7` | 比页面底略亮，形成层次 |
| 墨青（主色） | `#3f5c56` | 低饱和冷青，与暖白形成唯一的冷暖对冲 |
| 松绿（启用） | `#4c7a5f` | 低饱和，接近墨青的「同类色」 |
| 赭石（警告） | `#9a6b2f` | 暖色，唯一的高存在感语义色 |
| 赭红（危险） | `#9c4a3c` | 暖红，饱和度低于常规红 |
| 灰蓝（信息） | `#5b7285` | 冷灰蓝，中性 |
| 中灰（停用） | `#8d867a` | 暖灰，明确区别于危险 |

> 关键约束：**墨青、松绿、灰蓝同属冷色低饱和家族**，赭石与赭红同属暖色家族，
> 页面整体因此呈现「冷主调 + 暖点缀」的两层结构，
> 语义色不会与主色争夺注意力，也就不会「配色太杂」。

### 13.4 统一标准（方案 E 的规范）

所有控件遵守同一套规格，写在 `frontend/src/styles/theme/calm-paper.css`：

```
圆角：控件 4px · 卡片 12px · 浮层 8px
边框：全部 1px，主边框 #e2ddd1，分隔线 #ece7dc
状态条：4px 圆角 + 1px 边框 + 语义色 0.14 透明度底 + 语义深色文字 + 7px 实心圆点
按钮：4px 圆角 + 1px 边框 + 极淡底色；主按钮墨青实底，其余描边
焦点：2px 主色 22% 透明度外圈，不使用高亮色块
字号：沿用全局三档（标准 14px / 大 16px / 特大 18px），不另起一套
```

### 13.7 主题隔离

与方案 D 同一机制：`data-spd-theme="calm-paper"` 挂在 `<html>` 上，
与用户主题切换器的 `data-theme` 隔离。实测浅色原版页：

```
data-spd-theme = null
表头底色 = rgb(31, 111, 109)     ← 仍是青玉
数据格 border-right = 1px        ← 竖线仍在
```

方案 E 与方案 D 完全互不影响，可同屏对照。

### 13.8 与浅色页共用的能力

同一后端接口、同一套 `useListColumns` 列宽算法（`fitMode: 'hybrid'`）、
同一套筛选 / 分页 / 列设置 / 批量维护 / 增删改停启用、同一套三档字号。
功能与浅色原版**完全对齐**，实测筛选、空态、重置、行内编辑弹窗均正常。
