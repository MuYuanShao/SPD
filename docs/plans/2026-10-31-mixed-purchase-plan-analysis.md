# 混合采购计划与审批自动拆单：根因及解决建议

实施更新：已按本方案完成修改和本地V107升级，详见 [修复与验收记录](../reviews/2026-10-31-mixed-plan-fix-verification.md)。下文保留修复前分析及建议。

日期：2026-10-31。本次只读核验代码、数据库结构、第二轮实测记录及审计日志，没有修改业务实现或新增采购单据。

## 核实结论

两个问题均已确认。当前系统实现为“单商品、单供应商计划 → 人工审批 → 人工执行转单”，与用户要求的“混合计划 → 最终审批 → 按明细配送商自动生成多个采购订单”不一致。

这不是MCP传输失败，也不是管理员缺少审批权限。计划最终审批已经成功，订单创建函数却只在 `execute` 分支调用；审批分支没有自动转单逻辑。

| 环节 | 当前实现 | 目标行为 |
| --- | --- | --- |
| 计划模型 | 计划头存单一商品、供应商、数量 | 计划头＋多条商品明细，每条明细有配送商 |
| 生成计划 | 每条需求商品生成一个计划号 | 一次选定的混合需求建立一个计划头 |
| 最终审批 | 只更新approved | 最终审批成功后按配送商生成订单 |
| 计划与订单关系 | converted_order_no单字段 | 同一计划一对多采购订单 |
| MCP上传 | 每张订单反查一个converted_order_no | 每张供应商订单保留同一来源计划ID及其自身明细 |

## 一、混合计划为什么无法生成

1. `purchase_plan` 表直接保存 `supplier_id`、`product_id`、`planned_quantity`，没有计划明细表。2026-10-31只读核验确认 `purchase_plan_item` 不存在。`converted_order_no` 也只能表达一个订单号。
2. `PurchaseOrderService.createPlanFromDemands`（533行）查询需求商品；572行开始逐商品循环，每次生成新计划号并插入计划头。因此哪怕两个耗材来自同一需求，也会建立两张计划。不是先按供应商分组，**即使配送商相同，多商品仍可能形成多张计划**。
3. 当前前端还提供计划级供应商选择；后端请求中的 `supplierName` 会覆盖所选商品的供应商。缺少有效供应商时又使用 `findFirstEnabledSupplierId()`。这两种行为均不能代替“按明细配送商”拆单，可能掩盖配送商配置错误。
4. `createOrderFromPlan`（823行）只读计划头的一组商品、供应商、数量，建立一张单商品订单；仅调整前端勾选或把循环外移，无法完成可靠修复。

第二轮实测：需求 `XQ202610300002` 同含低值20支和高值4支，接口返回 `createdPlans=2`，计划分别是 `JH202610300003`、`JH202610300004`。数据库及create_from_demand审计记录均印证这个结果。

## 二、审批后不自动生成订单的核实

`PurchaseFlowRules.nextPlanStatus` 明确区分两个动作：

```text
approve：draft → approved
execute：approved → executed
```

`PurchaseFlowCommandRunner.runPlanAction`：

- 130行先记录审批决定；未到最终步骤时保持原状态，这个审批门槛需要保留。
- 133—136行的approved分支只更新状态、审批时间并写审计，然后直接返回。
- 138行后的executed分支才调用 `orderFromPlanFactory.apply(...)` 创建订单，并保存converted_order_no。

前端 `PurchaseManagementView.vue` 442—443行分别展示“计划审核”和“转订单”；测试 `PurchaseFlowCommandRunnerTest.planExecuteCreatesOrderAndStoresConvertedOrderNo` 也只验证execute建单。因此**这是当前设计缺少自动建单触发点，不是已存在自动任务偶发失效**。

第二轮在每张计划最终审批后立即采集到 `orderNo=null`。随后为了完成下游测试，明确手动执行execute，才生成 `CG20261030003`、`CG20261030004`。本次只读审计核验确认每张计划均存在先approve、后execute的记录。不能用现在已经executed的状态证明“当时审批自动建单”。

核验证据：[只读结构与审计结果](D:/SPD-PR/output/dual-supplier-flow/plan-root-cause-evidence-20261031.json)、[第二轮完整实测](../reviews/2026-10-30-two-supplier-round2-test.md)。

## 三、推荐修复方案

### 1. 改为计划头＋计划明细

通过后续Flyway迁移实现，不手工改业务库：

- 计划头保留计划号、审批状态、申请人/科室、备注、审批时间等单据属性；供应商与高低值不作为分单依据。
- 新增 `purchase_plan_item`，保存稳定明细ID、来源需求明细、商品、数量、单位、明细配送商，以及审批所依据的价格/金额等必要快照。
- 配送商在计划明细中明确展示并在审批前确认，不能仅在转单时读取可能已变化的医院目录供应商，也不能缺失时随意选择第一个启用供应商。
- 删除“计划头统一供应商覆盖全部明细”的常规入口；如需批量设置，也必须作用到可见的具体明细并重新参与审批。
- 计划列表按单据显示，点开可查看混合明细及各明细配送商；不能把不同单位的数量直接相加展示为一个总数量。

### 2. 最终审批完成后自动按配送商拆订单

在最终审批通过的服务事务中执行：

```text
锁定计划及明细
→ 校验所有明细和配送商
→ 确认审批流全部通过
→ 按明细配送商分组
→ 每组创建一张采购订单及对应明细
→ 保存计划与所有订单关联
→ 写审批、拆单审计及上传状态/消息
→ 一次提交
```

同一配送商的高值和低值应进入同一订单，不再因高低值二次拆单。不同配送商分成不同订单，所有订单共同引用同一原计划。

只在最终审批步骤触发，不在第一步“点通过”或前端页面回调触发。任何明细配送商缺失、停用、数量无效或建单失败，应使该次最终审批/建单事务回滚，返回明确错误，不能留下半张计划的订单。

生成订单后的状态也必须明确：现有MCP供货要求SPD订单为approved或sent。若自动建单仍产生draft，必须保留并清楚说明后续订单审批/发送步骤；若采用“计划审批即完成采购授权”的业务规则，则应以该审批来源设置可履约订单状态并保留审核依据，不能无审计地跳过现有规则。本次确认的是自动生成订单要求，不把“生成草稿”暗中等同于“已可供货”。

### 3. 建立稳定的一对多来源关系及幂等

- 采购订单增加明确的来源计划ID；订单明细关联来源计划明细ID。
- 一次拆单时，以来源计划＋配送商建立唯一约束或等效的拆单关系表，防止重复点击、并发审批或重试创建重复订单。
- 同一计划再次提交最终审批/转单请求时返回既有订单列表，不能重复分配数量。
- API返回 `orderNos`/订单列表；不能只返回或保存一个orderNo，也不能把多个订单号拼到原单值字段作为主要关系。
- 兼容旧execute入口时，让它调用同一个幂等拆单服务；新单不再要求操作员另点“转订单”。历史已审批但未转单的单据应通过受控、可审计的补生成入口处理，不在启动时无差别批量生成。

### 4. 同步修正MCP来源与供应商隔离

`McpUploadJob.uploadOrders` 131行当前通过 `purchase_plan.converted_order_no` 反查来源，需要改为使用订单的直接来源关系，保证A、B订单携带相同的原计划身份和各自稳定订单明细ID。

`McpPhase3Outbox.capturePlan` 当前也按计划头单供应商、单商品生成计划报文。混合计划改造时必须同时处理，否则可能漏上传或向一个供应商暴露其他供应商明细。建议：

- 供应商订单仍是履约主单据，上传时仅含本配送商明细。
- 如继续提供MCP“医院采购计划”查询，为各供应商提供独立稳定的投影视图/来源身份，保留共同院内计划号；不可将完整混合计划假装属于某一个供应商，也不可用一个sourceId在不同供应商之间反复覆盖。
- 沿用现有重试与幂等机制。网络发送在业务事务外完成；MCP暂不可用不应撤销已经合法生成的院内订单。

### 5. 历史兼容

旧计划每条回填为一条计划明细，保留原计划号、审批和订单关联。已经生成、上传或履约的历史计划不得强行合并改号。新的混合规则从升级后新建计划开始生效，避免破坏MCP已经保存的来源身份及历史审计。

## 四、建议验收标准

1. 一张计划含MCPg和MCPd，分别指定A/B配送商；最终审批后自动生成两张订单，来源计划号相同，数量分别20和4。
2. 相同配送商同时供应高低值时只生成一张订单，内含两类明细。
3. 多级审批未全部完成不建订单；最终审批完成只生成一次，接口直接返回全部订单。
4. 重复请求、并发审批、消息重试不重复建单；不同配送商建单中途失败时整组回滚。
5. 缺少配送商不自动选择其他供应商；审批后修改配送商不得静默改变已审批/已生成订单。
6. MCP A/B账号只能查看并供货自己的订单和计划投影，不能读取对方明细。
7. 原供货回传、SPD收货、唯一码占用、签收、消耗及结算链路继续通过；历史单据关联不变。

建议将混合计划模型与最终审批自动拆单作为同一次业务改造实施。只修自动触发，会继续得到“多个单商品计划各建一单”；只修计划列表或混合表单，也不能满足审批后的自动履约流程。
