## 7. 缺陷与改进建议

| 优先级 | 问题 | 建议 |

| P0 | 本地默认管理员账号不能登录，现有可登录账号又无审批角色，导致核心审批闭环无法验收 | 修复本地种子账号口令一致性；提供一个明确的本地审批测试账号并通过 Flyway 授权 |

### 11.3 隔离结论与缺陷

当前数据隔离为“部分生效”，不能作为权限验收通过：

1. 用户列表和采购需求列表已经接入 `DataScopeService`，其读取隔离能够按角色生效。
2. 采购需求创建接口信任请求中的 `deptName`，未校验目标科室是否在当前操作员的数据域内，存在跨科室写入风险。
3. 医护角色为“本人”数据域，但采购需求没有创建人字段参与过滤，造成可写不可读。
4. Spring Security 当前仅校验是否登录，未按 `sys_role_permission` 对 Controller/API 做授权；前端路由也只校验登录状态。因此已分配的功能权限目前是配置数据，不能形成真正的访问控制。
5. 科室申领等业务列表尚未统一接入数据域过滤，存在跨科室读取风险。

缺陷建议：

| 优先级 | 缺陷 | 修复建议 |
| --- | --- | --- |
| P0 | 任意登录用户可访问系统角色/权限接口，接口层没有权限点校验 | 在后端引入权限码授权并保护用户、角色、权限的读写接口；前端菜单与路由同步按权限码过滤，但以后端为最终边界 |
| P0 | 采购需求可跨科室写入 | 创建时忽略普通用户传入的科室，使用 `OperatorContext.deptId`；具备跨科室权限的角色才允许显式选择，并在服务层校验数据域 |
| P1 | 申领等业务列表跨科室可见 | 为所有科室归属的读模型统一接入 `DataScopeService`，详情和状态变更接口也必须校验所属科室 |
| P1 | “本人”域采购需求可写不可读 | 给采购需求保存 `create_by` 并提供 owner 列过滤，或禁止医护角色进入采购需求创建功能，二者应选定一致的业务规则 |

复测退出条件：无系统管理权限账号访问系统管理 API 返回 403；跨科室创建和状态变更返回明确中文错误；列表、详情、导出和操作接口使用同一数据域规则；上述 4 条带 `ISO-20260713-*` 标记的数据均能按预期归属验证。
